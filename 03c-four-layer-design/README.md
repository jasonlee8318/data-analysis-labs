# 4계층 분석 시스템 설계 과제 — 수집·저장 / 처리 / 분석 / 시각화

**이건 설계 단계**입니다. 코드나 docker 명령 없이, 분석 시스템 전체를
4개 계층(수집·저장 / 처리 / 분석 / 시각화)으로 어떻게 구성할지 종이
위에서 먼저 판단해봅니다.

> 이 과제를 마친 뒤 `../03-architecture/`(4계층 파이프라인 코드 실습)로
> 넘어가면, 여기서 설계한 계층 구조가 실제 코드에서는 무슨 일을 하는지
> 확인할 수 있습니다 — "설계 → 구현"으로 자연스럽게 이어집니다.

`03b-worker-scaling-design`(Spark 클러스터 확장 설계)과는 주제가
다른 별개의 심화 과제입니다.

## 이 과제가 다루는 것

이론 시간에 배운 4계층 구조(수집·저장 → 처리 → 분석 → 시각화)는
"각 계층에 어떤 도구가 있는지" 아는 것과, "내 상황에 어떤 도구를 왜
골라야 하는지 판단하는 것"이 다른 능력입니다. 이 과제는 후자를
연습합니다.

## Warm-up — 요구사항에서 설계 조건 뽑아내기

다음은 이론 시간에 다룬 요구사항입니다.

> "최근 3년간 1억 건의 고객 행동 로그를 분석하여, 매일 새벽 이탈 예측
> 모델을 갱신하고 대시보드를 자동 업데이트한다."

이 한 문장 안에는 시스템 구조를 결정하는 **4가지 조건**이 숨어 있습니다.
빈칸을 채워보세요.

| 조건 | 이 문장에서 찾은 값 |
|---|---|
| 데이터 규모 | |
| 분석 범위(기간) | |
| 처리 주기 | |
| 운영 조건(자동화 대상) | |

이 4가지 조건이 곧 아래 본 과제에서 계층별 도구를 고를 때의 **판단
근거**가 됩니다.

## 본 과제 — 시나리오별 4계층 설계

아래 표를 시나리오마다 채우세요. **정답이 정해진 문제가 아니라,
조건에 맞는 도구를 골랐는지·왜 다른 도구를 고르지 않았는지가 핵심**입니다.

### 작성 항목

| 계층 | 선택한 도구 | 선택 이유 |
|---|---|---|
| ① 수집·저장 | | |
| ② 처리 | | |
| ③ 분석 | | |
| ④ 시각화 | | |

추가로 각 시나리오마다 아래 두 질문에도 답하세요.

- **배치 vs 실시간**: 이 시나리오는 배치 처리, 실시간 처리, 혹은 두 방식을
  섞어야 하나요? 어느 계층에서 그 구분이 갈리나요?
- **트레이드오프**: 이 설계를 선택함으로써 포기하는 것(비용, 속도, 구현
  복잡도 등)은 무엇인가요?

---

### 시나리오 A — 기준 시나리오 (이론 시간의 그 요구사항)

> Warm-up의 요구사항 그대로: 3년치 1억 건의 고객 행동 로그, 매일 새벽
> 이탈 예측 모델 갱신, 대시보드 자동 업데이트.

- 힌트 질문: 로그가 "매일 새벽 처리"라고 해서, 로그가 발생하는 시점도
  반드시 새벽이어야 할까요? 수집과 처리의 시점은 같아야 하나요?

### 시나리오 B — 실시간 이상 거래 탐지

> 카드사가 결제 거래를 분석해 부정 사용을 탐지하려 한다. 거래가 발생한
> 후 수 초 안에 이상 여부를 판단해 결제를 막아야 한다. 하루 거래 건수는
> 이커머스 로그보다 훨씬 적다(수백만 건 수준).

- 힌트 질문: 데이터량이 시나리오 A보다 훨씬 적은데도 왜 더 어려운
  시스템이 될 수 있을까요? "규모"와 "속도 요구사항" 중 이 시나리오를
  어렵게 만드는 건 어느 쪽인가요?

### 시나리오 C — 소규모 스타트업의 주간 마케팅 리포트

> 직원 10명 규모의 스타트업이다. 월간 방문자 데이터는 100만 건 수준이고,
> 매주 월요일 아침 지난주 마케팅 성과 리포트를 담당자가 확인하면 된다.
> 예산은 매우 제한적이다.

- 힌트 질문: 이 규모에서도 Spark와 4계층 전체 구성이 꼭 필요할까요?
  "도구가 있다고 다 써야 하는 건 아니다"라는 이론 시간의 메시지를
  이 시나리오에 적용해보세요.

### 시나리오 D — 실시간 수집 + 배치 분석이 섞인 제조 현장

> 공장 설비에서 센서 데이터가 1초마다 발생한다. 데이터는 계속 실시간으로
> 모아두되, 정밀한 고장 예측 모델은 하루 치 데이터를 모아 매일 밤
> 재학습한다. 다만 설비 온도가 위험 수준을 넘으면 그 즉시 알림이 가야 한다.

- 힌트 질문: 이 시나리오는 같은 데이터를 두 가지 경로로 써야 할 수도
  있습니다. "즉시 알림"과 "매일 밤 모델 재학습"이 같은 처리 계층 도구를
  써도 될까요, 아니면 나눠야 할까요?

## 산출물

시나리오별로 위 표(4계층 도구 선택 + 이유, 배치/실시간 판단, 트레이드오프)를
채운 문서. 발표를 진행한다면 "왜 다른 도구를 고르지 않았는지"를
질문해보는 것이 트레이드오프를 얼마나 깊이 고민했는지 확인하는 데
효과적입니다.

---

## (강사용) 채점 방향

- **A(기준 시나리오)**: 이론 슬라이드의 예시 도구(Kafka/DB/S3, Spark,
  MLlib/scikit-learn, Power BI/Tableau)를 그대로 나열하는 데 그치지
  않고, "왜 이 조합인지"를 4가지 조건(규모/기간/주기/자동화)과
  연결해서 설명했는지가 핵심입니다. 힌트 질문에 대해서는 "수집은
  실시간으로 계속 쌓아두고, 처리·분석만 새벽 배치로 도는" 구조를
  스스로 도출하면 우수합니다.
- **B(실시간 탐지)**: 데이터량이 적다고 시스템을 가볍게 설계하면 안
  된다는 걸 짚었는지 확인하세요. "규모"가 아니라 "지연 허용 범위"가
  설계를 좌우한다는 게 핵심 포인트입니다. Kafka + Spark Structured
  Streaming 같은 실시간 처리 계열을 스스로 끌어왔는지가 관건입니다.
- **C(스타트업)**: "4계층을 전부 갖춰야 한다"는 강박에서 벗어나,
  Python 스크립트 + 간단한 DB + 엑셀/Google Sheets 정도로도 충분하다는
  판단을 내렸는지가 핵심입니다. 과잉 설계를 지적하는 것 자체가
  학습 목표입니다.
- **D(혼합형)**: 같은 데이터라도 목적에 따라 처리 경로를 분리해야
  한다는 걸 이해했는지 확인하세요("즉시 알림"용 실시간 스트림 처리와
  "모델 재학습"용 배치 처리가 병행되는 구조). 두 경로를 하나로
  뭉뚱그리려 한 답변은 재고를 요청하는 것이 좋습니다.

공통적으로, **계층마다 도구 이름만 나열하고 이유가 없는 답변**은
재작성을 요청하는 것이 좋습니다 — 이 과제의 목적은 도구 암기가 아니라
"조건에 맞는 선택"을 연습하는 것입니다.
