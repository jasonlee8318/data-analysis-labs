# 12강 — 분석 시스템 검증 및 개선

새로운 도구는 배우지 않습니다. **1부**는 지금까지 만든 모듈들이
각자 정상 동작하는지, 그리고 일부는 실제로 하나의 파이프라인으로
이어지는지 확인하는 통합 테스트입니다. **2부**는 "모델을 한 번 만들고
끝"이 아니라 "언제, 어떻게 다시 학습시킬지"를 설계하는 재학습 전략
과제입니다.

## 참고 — 이 과정의 실습들은 완전히 하나로 이어진 파이프라인이 아닙니다

엣지 컴퓨팅 과정과 달리, 이 과정의 실습들은 회차마다 다른 데이터를
씁니다 (3~5회차는 회원/주문 데이터, 6·8회차는 카페 매출 데이터, 10·11회차는
이탈 예측 데이터). 그래서 "전체를 한 줄로 잇는" 통합 테스트가 아니라,
**① 각 모듈이 독립적으로 잘 동작하는지 확인**하고 **② 실제로 이어지는
구간(8회차 전처리 → 6회차 시각화)은 진짜 파이프라인으로 검증**하는
두 가지 방식을 섞어서 진행합니다.

## 2부 — 재학습 전략 설계 과제

코드나 docker 명령은 필요 없습니다. 아래 시나리오를 읽고 재학습 전략을
설계하세요.

### 시나리오

> 10~11강에서 만든 이탈 예측 모델을 실제 서비스에 배포해 매주 이탈
> 위험 고객 리스트를 뽑아 마케팅팀에 전달하고 있다. 배포 3개월 후,
> 마케팅팀이 "요즘 리스트에 오른 고객 중 실제로 이탈하는 비율이
> 예전보다 낮아진 것 같다"는 피드백을 줬다.

### 작성 항목

| 질문 | 답변 |
|---|---|
| 1. 모델 성능이 떨어졌다는 걸 마케팅팀의 "느낌"이 아니라 데이터로 어떻게 확인할 것인가? | |
| 2. 성능 저하의 원인일 수 있는 것을 2가지 이상 추측한다면? (예: 고객 행동 패턴 변화, 계약 정책 변경 등) | |
| 3. 재학습은 얼마나 자주 하는 게 적절한가? (매일/매주/매월/성능 저하가 감지될 때만) 그렇게 정한 이유는? | |
| 4. 재학습 전/후 모델 중 무엇을 실제 서비스에 반영할지 어떻게 검증할 것인가? (예: A/B 테스트) | |
| 5. 재학습한 모델이 오히려 더 나쁘다면, 어떻게 되돌릴 것인가? | |

### (강사용) 채점 방향

- **1번**: "성능이 떨어진 것 같다"는 느낌을 실제 검증 가능한 지표(예:
  최근 예측 대비 실제 이탈률, AUC 재계산)로 바꿔 표현했는지가 핵심입니다.
- **3번**: "무조건 자주 재학습"이 아니라, 재학습 비용(연산 자원, 검증
  시간)과 성능 저하 속도 사이의 트레이드오프를 언급했는지 확인하세요.
- **4번**: 재학습된 모델을 검증 없이 바로 전체 서비스에 반영하려는
  답변은 재고를 요청하세요 — 일부 트래픽에만 먼저 적용해보는 점진적
  검증 개념이 나와야 합니다.
- **5번**: "롤백"이라는 개념 자체를 스스로 떠올렸는지가 핵심입니다.
  이전 모델을 보관해두지 않으면 되돌릴 수 없다는 점까지 짚으면 우수합니다.

공통적으로, **"모델을 다시 학습시키면 된다"는 한 줄짜리 답변**은
재작성을 요청하는 것이 좋습니다 — 이 과제의 목적은 재학습이라는
행위 자체가 아니라, 그걸 둘러싼 판단(언제/어떻게/검증/롤백)입니다.
